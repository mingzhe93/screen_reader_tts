# v0.3.0 Assistant tools plan: tool calling, web search, a Python sandbox and thinking in voice

Status (2026-10-19): the settled scope is implemented in the working tree; integrated tests and real-model qualification are recorded in [assistant/tools.md](assistant/tools.md) and §16 below. Builds on [v0.3.0_assistant_plan.md](v0.3.0_assistant_plan.md) (Steps 1–5, committed as `5e62732`). The app version is now `0.3.0`, in release preparation. I have tested and accepted the current macOS app, and Windows since 2026-10-20. Sections 2–15 retain the research/design sequence, with superseding implementation details in §16–17 and the linked implementation guide.

Decisions I accepted exactly as recommended are marked **(AI-recommended)** so they get a second look. Unmarked decisions came from me or were changed during discussion.

## 1. Goal

Let the Assistant answer questions that need current information or exact computation, in chat and in voice mode, without giving up its speed or the "nothing leaves this computer unless you say so" default.

The models do not need to be the smartest. Knowing when to call a tool, and calling it correctly, matters more. Speed matters because voice mode runs speech recognition, the model and TTS together.

## 2. Evidence gathered before deciding

All on the M2 Max with the pinned llama-server b11718 (`--jinja --reasoning-format deepseek --parallel 1`). Scripts are in the session scratchpad; the results are recorded here so nobody has to rerun them to understand the decisions.

**Tool calling per model** (a `get_weather` and a `web_search` tool, thinking off unless noted):

| Check | MiniCPM-V 4.7 1B | Gemma 4 E4B | Gemma 4 12B |
|---|---|---|---|
| "Weather in Singapore?" calls `get_weather{"city":"Singapore"}` | yes | yes | yes |
| Same, streamed | yes | yes | yes |
| Correct answer from the tool result | yes | yes | yes |
| "What is 17 times 23?" answered without a tool | **no**: called `get_weather` for Los Angeles | yes | yes |
| "Apple's stock price today?" with thinking on searches | yes | yes | yes (added the date to the query) |

llama.cpp already converts each model's own tool-call format into OpenAI `tool_calls`, streamed and non-streamed. At this initial probe, MiMo-V2.6 9B had not been tested (download pending); the later full qualification failed the required bar (§16). its chat template uses the Qwen3-Coder XML call format (`<tool_call><function=…>`).

**Server behaviour** (b11718):
- **Per-request thinking budget:** the undocumented body fields `thinking_budget_tokens` and `reasoning_budget_tokens` both cut reasoning, identically to the `--reasoning-budget N` server flag. `reasoning_budget`, `thinking_budget`, `max_thinking_tokens` and `chat_template_kwargs.thinking_budget` are silently ignored. The cut is abrupt (mid-sentence); the answer still arrives in full. `--reasoning-budget-message` is appended inside `reasoning_content`, with no separator, so it is never spoken or shown as the answer.
- **Streaming tool arguments:** arguments stream incrementally as JSON fragments. Gemma E4B: first fragment at 0.37 s, call complete at 1.02 s; MiniCPM: 0.23 s and 0.45 s. **Gemma emits arguments in alphabetical key order**, whatever the schema order (`query` before `spoken_status`); MiniCPM follows schema order. MiniCPM also streamed plain content ("I will search for…") before its call.
- **Prompt cache across a tool round:** only the new suffix is re-processed (Gemma: 54 of 331 tokens; MiniCPM: 40 of 576). With thinking on, stripping the old reasoning breaks the prefix at that assistant turn, costing about 30–50 extra tokens; the hybrid recurrent model (MiniCPM, same `qwen35` architecture as MiMo) recovered without a full re-process.
- **Reasoning across tool rounds:** rendering a two-round tool conversation with `/apply-template` shows that the Gemma 4 and MiniCPM templates keep the reasoning of every tool round after the last user message and drop earlier turns' reasoning, with either `--reasoning-preserve` setting. The MiMo template renders `reasoning_content` for every assistant message it is given, so the loop must send reasoning only for the current turn's rounds (§5.5).
- **A loop hazard:** with thinking on, MiniCPM called `get_weather` again after receiving its result, in two separate runs.

**How Unsloth Studio does it** (read for ideas only; it is AGPL-3.0, so no code is copied): web search through the `ddgs` library, which scrapes DuckDuckGo, Brave, Wikipedia, Mojeek and Startpage with browser impersonation, engine fallback and retries, then fetches pages; code runs as real Python/Bash under per-OS sandboxes (macOS Seatbelt with a default-deny profile that still allows network, Linux Landlock + seccomp, Windows Microsoft MXC 0.8.0 alpha); about 250 KB of tool-call parsing and repair code; tools on by default only on localhost.

**Python on WebAssembly** (initial research, before implementation; later results are in §16):
- CPython's `wasm32-wasip1` target is Tier 2 from 3.13 (PEP 11). There is no python.org download; prebuilt builds come from [brettcannon/cpython-wasi-build](https://github.com/brettcannon/cpython-wasi-build/releases) (Brett Cannon is a CPython core developer). 3.14.7: a 14.3 MB zip, 40.8 MB unpacked, `python.wasm` 30.5 MB, stdlib as `.py` files, PSF licence.
- Built in: `_decimal`, `_json`, `_csv`, `_datetime`, `_zoneinfo`, `math`, `_statistics`. Missing: threads, `subprocess`, `ssl`, `zlib`, and **the time-zone database** (must be supplied).
- `wasmtime` 49 needs Rust 1.96; the toolchain here is 1.94.1. The **36.x LTS** line needs 1.86. Epoch interruption gives a cheap wall-clock limit; `StoreLimits` caps linear memory; WASI preview 1 has no sockets unless granted; `Engine::precompile_module` + `Module::deserialize` avoid recompiling the 30 MB module per run. Binary-size impact is unmeasured.

## 3. Scope

One phase (the user's choice; the committed `5e62732` is the rollback point):
1. A tool loop in chat **and** voice mode.
2. Tools: `web_search`, `fetch_page`, `get_weather`, `run_python`.
3. A Python sandbox (WebAssembly).
4. Thinking in voice mode, with spoken fillers and a thinking limit.

Out of scope: charts and numpy/pandas; file outputs from code; a home-location setting; IP geolocation; summarising older tool results (later, §11); custom models or API endpoints.

**Definition of done:** these pass on Gemma 4 E4B and MiMo-V2.6 9B, in chat and by voice (d is chat only), in the automated tool test (§9) and once live:
- (a) "What's the weather today?" (the model asks which city, then answers)
- (b) "What's Apple's stock price?" (through search, saying it may be delayed)
- (c) "What's the latest news on X?"
- (d) "Summarise this page: <url>" (chat only)
- (e) A question that needs no tool does not call one. *(AI-recommended, with the user's change to d)*

## 4. Policy

- **Privacy:** tools are **off by default**. The Assistant-page wrench menu has All tools, per-tool switches and independent Chat/Voice selections. The first enable explains the provider requests and optional code-runner download before asking for consent. Only enabling Python prepares its approximately 15 MB runtime; network-only selections do not. This replaces the original globe toggle; see §17.
- **Automatic runs:** all four tools run without asking, are always visible in chat and in the voice transcript, and are cancelled by Stop or an interruption. Code runs automatically because isolation is the safety measure; code is shown in chat and never spoken. *(AI-recommended)*
- **Which models:** each catalogue model gets a `tools` flag, set from the automated test (§9: 11 of 12 or better). Gemma E4B and 12B are expected to qualify; MiMo after its test. **MiniCPM** is not flagged and is not expected to pass, but the user may still switch tools on for it, after a second confirmation: "This is a small model; tool use may be unreliable." The flag only sets the default and the warning; it never blocks.
- **Location:** no home-city setting. When a tool needs a place the user did not give, the model asks.

## 5. Tool loop

### 5.1 Where it runs *(AI-recommended)*
In Rust, inside the existing chat bridge (`assistant_chat.rs`). Voice mode already goes through it (`assistant_conversation.rs` streams the bridge into a `VoiceSink`), the llama-server API key stays in Rust, and the fetch allowlist and network guard live next to the code that fetches. The page only renders events.

### 5.2 The loop
1. The request carries `tools`, the selected `enabledTools` list and the app-owned tools prompt (§7.4). The turn snapshots its capabilities, filters the schemas and rejects disabled calls before execution.
2. Stream as today. Content deltas go to the sink. Tool-call deltas are accumulated per index; the name and argument fragments are forwarded as they arrive (`assistant:tool-call`, §8), so fillers can start early (§6.2).
3. When the stream finishes with `finish_reason: "tool_calls"`, validate and run the calls (sequentially, in the order given), emitting `assistant:tool-result` for each, then send the next request: the history plus the assistant message (with `tool_calls`, and `reasoning_content` per §5.5) plus one `tool` message per call.
4. Repeat until the model answers without a tool call, or the round limit is reached.

### 5.3 Guards *(AI-recommended, with the user's "configurable")*
- **Round limit:** default 5 tool rounds per turn, configurable 1–20. The request for the last allowed round omits `tools` (or sends `tool_choice: "none"` if the template needs the definitions kept), so the model must answer.
- **Repeats:** a call identical (same name, canonicalised arguments) to an earlier one in the same turn is not run; the model receives `{"error": "Already done in this turn; use the earlier result."}`.
- **Malformed calls:** unknown tool, unparseable JSON or arguments failing the schema return an error message to the model, which gets one retry per turn; a second malformed call ends the loop and the model answers without tools.
- **Time limits (configurable):** search 8 s, fetch 10 s, weather 5 s, code 60 s. The code limit covers running the code only, not the time the model spends writing it.
- **Cancellation:** Stop, an interruption or read-aloud preemption cancels the model request and any running tool (a cancel token checked by every tool; the sandbox is stopped by its epoch deadline).

### 5.4 History *(AI-recommended)*
Tool results stay in the context for the current turn only. Afterwards the stored history holds the user's message, the final answer and a short note, for example `(searched: "Apple stock price"; sources: 1. reuters.com …)`. A follow-up that needs more detail makes the model search again. Same for chat and voice. Later: idle-time summarisation (§11).

### 5.5 Reasoning *(AI-recommended, verified)*
Within a turn, the assistant messages of earlier tool rounds are sent back with their `reasoning_content`, so the model keeps its plan. Reasoning from earlier turns is never sent (the page already drops it from history). The server flag `--no-reasoning-preserve` stays as it is; it does not affect this (§2).

### 5.6 Context fitting
The existing `fit_to_context` budget applies to every round, counting tool messages. If a round would not fit, the oldest tool results of the current turn are truncated first, then the loop answers without more tools.

## 6. Voice mode

### 6.1 Thinking in voice
A "Think before answering" toggle in the voice panel, **off by default** *(AI-recommended)*. Off means `enable_thinking: false` and `reasoning_effort: "none"`, as today.

### 6.2 Fillers
The app writes them; the model does not *(AI-recommended)*. Gemma's alphabetical argument order and MiniCPM's question-shaped "status" lines ruled out a model-written `spoken_status` argument.

| Trigger | Filler (examples, varied) |
|---|---|
| Thinking still running 1.2 s after the request started, with no answer text yet | "Give me a moment." |
| Thinking still running, every ~6 s after that (not capped) | "Still thinking." / "Nearly there." |
| `web_search` call, once `query` has streamed | "Searching for {query}." |
| `fetch_page` call | "Opening that page." |
| `get_weather` call, once `city` has streamed | "Checking the weather in {city}." |
| `run_python` call | "Let me work that out." |
| A tool still running every ~6 s | "Still working on it." |

Queries are trimmed to about 8 words for speech. Fillers are recorded in the transcript in a muted style and never enter the model's history.

**Ordering (the user's requirement):** fillers are phrases in the same `AssistantSpeechJob` queue as the answer, ahead of it. The player plays phrases strictly in order, so answer text always waits until the filler has finished; on fast hardware nothing is cut off mid-word. A filler that has not started playing when the answer's first phrase is ready is still played (no dropping), but the timer fillers stop once answer text starts. Interrupting stops fillers and answer together.

### 6.3 Thinking limit
- A "Thinking limit" control in the panel's Advanced section, **separate for chat and for voice**: Auto, 256, 512, 1,024, 2,048, 4,096, 8,192, Unlimited, Custom (a whole number of tokens).
- Auto: **voice** is about 15 s of thinking on this machine, computed from its measured decode speed (`timings.predicted_per_second` of recent answers, with a conservative default before any measurement); **chat** is Unlimited. *(values AI-recommended)*
- Sent per request as `thinking_budget_tokens` (verified on b11718, §2).
- When the limit is hit, thinking stops and the model answers.

### 6.4 Turn-taking
A tool round counts as part of the answer: the microphone stays closed (auto mode paused) until the answer drains, the stall watchdog does not fire while a tool runs (the state line shows "Searching…" / "Running code…"), and pressing the talk button interrupts the tool and the answer.

## 7. Tools

### 7.1 `web_search` *(AI-recommended)*
- Parameters: `query` (string, required).
- Provider interface with two implementations:
  - **DuckDuckGo (default, no key):** the plain-HTML results page (`https://html.duckduckgo.com/html/`), an honest `VoiceReader/<version>` User-Agent, at most one search every 2 s, top 5 results (title, URL, snippet). Result links that go through DuckDuckGo's redirect are decoded to their target. No browser impersonation and no engine rotation. A CAPTCHA, a block or a changed page returns "Search is unavailable right now. You can add a Brave Search key in the Assistant Tools menu." and the model tells the user.
  - **Brave Search API (optional key in Assistant → Tools → Web search → Settings):** used instead of DuckDuckGo when a key is set.
- Returns about 600 tokens: numbered results with title, URL and snippet. The URLs join the turn's fetch allowlist (§7.2).

### 7.2 `fetch_page` *(AI-recommended)*
- Parameters: `url` (string, required).
- **Allowlist:** only URLs that appeared in this conversation's search results or in the user's own messages (exact match after normalisation; the same host with a different path is not enough).
- http and https only; no credentials in the URL.
- **Network guard:** resolve the host, refuse loopback, private (RFC 1918, unique local), link-local, CGNAT, multicast and unspecified addresses, then connect to the checked address (no second lookup). Redirects are followed manually (at most 5), each checked for a public destination and HTTPS downgrade. The initial model-selected URL needs an exact conversation grant; server-selected redirects may move to another public origin.
- No cookies; 10 s; 2 MB download limit; HTML, plain text and Markdown only (PDF later).
- Readable-text extraction (drop scripts, styles, navigation; keep headings, paragraphs, lists, tables as text), cut to about 6K tokens with a note when truncated.

### 7.3 `get_weather` *(AI-recommended)*
- Parameters: `city` (string, required).
- Open-Meteo geocoding (first match; the answer names the place found, so a wrong match is visible) and forecast APIs, no key. Current conditions plus today's high, low and precipitation chance, in °C with the time zone.
- Open-Meteo's data is CC BY 4.0: the source line credits it.

### 7.4 App-owned tools prompt *(AI-recommended)*
Appended after the user's (editable) system prompt, only when tools are on, so editing the prompt does not remove the app policy; allowed tools and argument/network permissions are also enforced in Rust. It contains: the current date, time and time zone; one line per tool on when to use it; "ask which city if the user did not say"; "say a stock price may be delayed"; "cite sources as [1], [2] matching the result numbers"; in voice only, "never read out web addresses; summarise in plain spoken sentences".

### 7.5 `run_python` *(AI-recommended, with the user's 60 s)*
- Parameters: `code` (string, required). The description says: Python 3.14 standard library only, no network, no files, a fresh interpreter each call, print the result.
- Returns stdout and stderr (with the traceback on failure), cut to about 4,000 characters, plus "timed out" or "out of memory" when a limit trips.
- Limits: 60 s (configurable), 256 MB of linear memory.

## 8. Contract additions (events and commands)

Events (payload fields snake_case, as elsewhere):
- `assistant:tool-call` `{request_id, round, call_index, call_id?, name?, delta, arguments?, phase, done}`: indexed fragments stream before the ID/name may be known; full arguments replace fragments when supplied. Phase is streaming/queued/running/done.
- `assistant:tool-result` `{request_id, round, call_id, name, status: "ok"|"error"|"timeout"|"cancelled"|"skipped", summary, sources: [{n, title, url}], output?}`: `output` is the code run's text for `run_python`.
- Voice: fillers are emitted as `assistant:voice-phrase` with a `kind: "filler"` field, so the transcript can style them.

Commands (invoke args camelCase):
- `assistant_chat_start` / `assistant_voice_respond` take `tools: boolean`, optional `enabledTools: string[]`, tagged `thinkingBudget` (Auto/Unlimited/Tokens) and a `toolLimits` snapshot; see [current contracts](assistant/chat.md).
- `assistant_tools_status` → whether the sandbox runtime is installed, its size and version.
- `assistant_tools_install` / `assistant_tools_delete`: the optional sandbox runtime, managed from Assistant → Tools → Python → Settings (Download/Delete).
- `assistant_set_search_key({ provider: "brave", key: string | null })` and `assistant_test_search_key()`: from Assistant → Tools → Web search → Settings; stored in the settings file (§15.4).

## 9. Checks

- **Automated tool test** *(AI-recommended)*: an `#[ignore]` Rust test that loads real models and serves **recorded** search, page and weather results from fixtures (no network). About 12 prompts: (a)–(e) with variations and 4 that need no tool. A model earns the `tools` flag at **11 of 12** or better. Run on Gemma E4B, Gemma 12B, MiMo and MiniCPM (expected to fail; recorded for reference).
- **Unit tests:** loop guards (round limit, repeats, malformed retry, cancellation), streamed argument assembly, the fetch allowlist and network guard (including redirect to a private address and DNS answers mixing public and private addresses), the DuckDuckGo HTML parser against saved pages (including a CAPTCHA page), filler timing and ordering, the thinking-budget calculation.
- **Sandbox tests:** a socket connection fails; reading outside the scratch folder fails; `zoneinfo.ZoneInfo("Asia/Singapore")` works; an infinite loop stops at the time limit; a large allocation stops at the memory limit; the scratch folder is empty after a run; startup time and first-run compile time are measured.
- **Manual:** (a)–(e) live once in chat and by voice on macOS, later on Windows.

## 10. Sandbox details *(AI-recommended)*

- **Runtime:** CPython 3.14 for `wasm32-wasip1` from brettcannon/cpython-wasi-build, pinned by release and SHA-256, plus the `tzdata` package (pinned) mounted read-only. Downloaded when Python is first turned on or requested from its settings, into `<assistant root>/sandbox/`, with the same staging, verification and rename steps as models; managed from Assistant → Tools → Python → Settings with Download/Delete.
- **Engine:** `wasmtime` 36 LTS with `wasmtime-wasi` (preview 1), embedded in the app (Base build only). The module is precompiled once per machine and wasmtime version and cached next to the runtime; later runs deserialize it.
- **Each run:** a new store and WASI context; argv `python -I -S -c <code>`-style (exact flags settled in implementation); stdin empty; stdout and stderr captured in memory with a size cap; preopened: the stdlib (read-only), tzdata (read-only), a fresh empty scratch folder (read-write, deleted afterwards); no environment variables; no network (asserted by test); epoch deadline from the configured time limit; `StoreLimits` memory cap.
- Runs off the async runtime (a blocking thread), one at a time.

| # | Finding | Resolution |
|---|---|---|
| F1 | `ChatMessage` (role/text/images) and `fit_to_context` cannot represent or count tool calls, tool results, reasoning or tool definitions; the fitter protects the last message, not the current user turn | New internal wire-message type (system/user/assistant with `tool_calls` and `reasoning_content`/tool, with `tool_call_id`). Counting goes through `/apply-template` with the real `tools` and messages. Eviction works on whole turns before the current one; inside the current turn, tool results are truncated (newest kept longest), then the loop forces a tool-free answer; the user message and each call/result pair are never split |
| F2 | "Round limit 1" disables tools entirely | The limit counts **tool-execution batches**: N batches, then one final tool-free request. Tests at 1 and 5 with exact request counts |
| F3 | Fillers and answer phrases both start at `seq` 0; fillers would count as heard answer text | The speech worker owns one job-wide sequence; every phrase carries `kind: "answer"\|"filler"`. Heard-text, history and highlighting use answer phrases only |
| F4 | Content a model writes before a tool call ("I will search for…") merges into the answer | **(user)** see §15 Q1. Either way: rounds have explicit boundaries, the phrase buffer is flushed at each, and only the final round's content is the answer |
| F5 | `max_tokens` and the context room can run out during thinking or mid-call | The thinking budget is per request and resets each round. The answer cap is `max(user max_tokens, thinking budget + 1,024)` when thinking is on, with the panel noting the raise. A `length` finish during a tool call never executes the call; the loop forces a tool-free answer |
| F6 | DNS checks are bypassed by system proxies; IPv4-mapped IPv6 unstated | Guarded fetches use a dedicated client with `no_proxy()`, the checked address pinned for the connection (`resolve`), and the original host kept for TLS/SNI. Addresses are canonicalised (IPv4-mapped/compatible IPv6 to IPv4) before classification; a DNS answer containing any non-public address is refused |
| F7 | Redirect rule contradicts the exact allowlist | The **model-chosen** URL must match the allowlist exactly. **Server-chosen** redirects (at most 5) may go to any public http(s) origin, each hop network-guarded, never https to http; the final URL is recorded as the source. (A redirect is chosen by the server, not the model, so it cannot carry the model's context out.) Tests: relative redirects, port change, downgrade, `%2F` versus `/` |
| F8 | No policy for instructions inside tool results | **(user)** see §15 Q2 |
| F9 | Provider clients: credential forwarding on redirect, unbounded bodies | Fixed provider origins; no redirects for Brave (a redirect is an error); the key only in the Brave client, never in messages, events or errors; body caps (search 1 MB, weather 256 KB); 401/429 mapped to readable errors |
| F10 | Writable scratch has no disk, file-count or descriptor limit; host memory is outside `StoreLimits` | **(user, with Q5)** Recommended: **no writable folder** in this phase (no file outputs), only the read-only stdlib and tzdata; WASI table and instance limits set; host RSS measured during compile and run |
| F11 | Deserialising a disk cache executes native code if the file is replaced | **(user, with Q5)** Recommended: compile once per app session and keep the module in memory; persist only if measured compile time makes that unworkable, then keyed by runtime hash, wasmtime version, config and target, written atomically, and hash-checked before use. The threat model excludes a local attacker with the user's own file access (who could equally replace llama-server) |
| F12 | Epochs cannot interrupt a blocked WASI host call (sleep) | **(user)** see §15 Q5 |
| F13 | Each HTTP completion currently ends the request (unregisters the slot, finishes speech, releases the use guard) | One registry slot, cancel owner and use guard per **turn**. Intermediate completions are non-terminal; exactly one terminal event per turn, after all tool events. Tests: cancel during fitting, between rounds, during a tool, racing the final answer |
| F14 | Unload, model switch, crash and exit do not cancel tool loops | Turns are bound to the backend generation; unload, load, crash and shutdown cancel every registered turn server-side and wait for tools to stop. A stale turn never sends to a new server |
| F15 | Sandbox install, delete and run have no shared lifecycle | States: not installed, installing, ready, failed. Runs hold a lease; delete waits for or refuses active runs; install and delete hold a cross-process lock (as the load lock does). Without a writable folder (F10) there is no scratch to clean up |
| F16 | Disabling the stall watchdog during tools hides a stuck filler | The watchdog stays on; a tool wait with nothing queued is already "not stalled", and queued filler audio that stops progressing still trips it |
| F17 | 11/12 lacks invariants, Python coverage and a fixed sampling protocol | Keep 11/12, plus hard invariants that must all pass: the city-clarification case, at least one successful `run_python`, no-tool cases, forced finalisation, a truncated call never executed. Pinned model, server, template, prompt and fixtures; seeds 1–3, temperature from the catalogue; a case passes on 2 of 3 seeds. MiMo's XML calls included |
| F18 | `assistant_voice_respond` cannot say whether thinking is on | Add `think: boolean` to it; `thinkingBudget` is a tagged value `{mode: "auto"\|"unlimited"\|"tokens", tokens?}` |
| F19 | Source numbering and fetch authorisation scope are undefined | Sources are numbered per turn across all calls ([1]…[n], never reused). Fetch authorisation is **conversation-scoped**: requests carry a `conversationId`; Rust keeps an in-memory allowlist per conversation, cleared by New chat and on restart. The terminal event carries the history note and the source list; an interrupted turn keeps its note and sources so far |
| F20 | Tool events lack lifecycle and fragment semantics | `assistant:tool-call` carries `delta` fragments (append), a stable `call_index` before the id and name are known, and a `phase: "streaming"\|"queued"\|"running"\|"done"`; all tool events for a turn precede its terminal event. A `assistant:turn-phase` event (`thinking`, `tool`, `answering`) drives fillers and state lines |
| F21 | Settings have no transport; Auto has no speed data; settings writes race | Tool settings live in the settings file behind a mutex-guarded update; each request carries a snapshot (`toolLimits`). Decode speed is taken from each response's `timings.predicted_per_second`, kept per model in memory, with a conservative default. Brave key storage: **(user)** §15 Q4 |

## 15. Decisions after the review (settled 2026-10-19)

1. **Content before a tool call (F4):** spoken as the model wrote it; the app's filler for that call is skipped when the model already said something in that round. Only the final round's content is the answer in history. *(AI-recommended)*
2. **Instructions inside tool results (F8):** the residual risk that a page makes an answer misleading is accepted. Tool results are wrapped as untrusted data in the tools prompt, and the spoken query filler uses the model's query only in the first round (before any web content is in context); later rounds say "Searching the web." Fetch stays allowlisted, search queries reach only the provider, code has no network or files. *(AI-recommended)*
3. **Commercial use (F22):** VoiceReader is distributed free and non-commercially, which Open-Meteo's free tier allows. Revisit before any paid distribution. *(AI-recommended)*
4. **Brave key storage (F21):** entered in the app, never by editing files. The Assistant page’s Tools menu owns the settings (superseding the original global Settings placement in §17): search provider (DuckDuckGo, or Brave when a key is set), a Brave Search API key field with Save, Remove and a "Test key" button, and a note that the key is stored in plain text in the app's settings file. The app writes it to the settings file itself. *(storage AI-recommended; Assistant-page placement is my later decision in §17)*
5. **Sandbox execution (F10, F11, F12):** wasmtime runs in-process with async support, so blocked WASI calls are cancellable and a timeout or Stop drops the run; epochs stop CPU loops; **no writable folder** (this replaces "a scratch folder wiped after each run"); the compiled module is kept in memory per app session, never written to disk. Compile time and host memory are measured early; caching on disk is revisited only if compiling per session takes seconds. *(AI-recommended)*

No new npm dependencies. Full builds exclude the optional Rust tool dependencies.

Integrated automated Rust and frontend checks pass, including the real Python WASI runtime. Live DDG search, public-page reading and Open-Meteo smoke checks passed. Measured first-session compilation is about 1.14 s and warm interpreter startup/execution about 0.12 s on the M2 Max. Installed runtime files are about 41.4 MB; a stress test filling guest memory reached about 538 MiB total host RSS, distinct from the 256 MiB guest cap.

## 17. Follow-up controls and extensibility (2026-10-19)

I tested tools working in both Chat and Voice after noticing the original globe control. I want more discoverable controls and room for additional tools. This section supersedes the globe/Settings/Models placement in the earlier design:

- A wrench **Tools** menu on the Assistant page, with All tools, per-tool switches, filtering and expandable tool-specific settings. Chat and Voice selections stay independent and off by default. Provider and limits are shared. Changes apply to the next message; both model schemas and execution use an immutable per-turn selection.
- Tool settings live only here: Web search owns the Brave key/provider/timeout; Weather and page reading own their timeouts; Python owns its timeout and optional runtime Download/Delete. Enabling network tools does not download Python. Shared execution-round limits remain under Advanced.
- Voice reasoning, when enabled, streams into a collapsed Thinking accordion like Chat. It is never spoken or included in later history, and expansion survives incoming fragments.
- Built-ins have per-tool Rust and TypeScript modules plus explicit registration lists. Shared dispatch and menu rendering do not match on tool names. Generic per-tool timeout overrides preserve compatibility with existing flat settings.
- I also want to ask the Assistant to create and add tools without rebuilding the app. I chose to **plan the plugin system now and implement it later**. [The separate plugin plan](assistant/tool-plugins-plan.md) records the workflow and proposed contracts. No runtime loader or chat installation is included in this implementation; capability/runtime choices remain open.
